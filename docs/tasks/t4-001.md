# t4-001: requirements to board

Tier 4 (cross-layer). The agent starts from the SysML v2 model
`SatcomTerminal28GHz` (sysml2kit-rf-library, model name
`satcom-terminal-t3001`) and submits a design bundle: a terminal
architecture, a patch element DesignSpec, a KiCad board for the element with
its provenance, and a verdict for every requirement, each reported number
carrying a provenance record. The task scores whether the bundle's claims
survive recomputation. How many requirements the design closes is reported
beside the verdict as a score.

Requirements (`tasks/t4-001-requirements-to-board/task.yaml`):

| id | metric | limit |
|---|---|---|
| verdict-agreement | `verdict_agreement` | >= 0.9 |
| actual-agreement | `actual_agreement` | >= 0.9 |
| provenance | `provenance_completeness` | >= 0.95 |
| board | `board_valid` | >= 1 |
| no-unrecognized-verdicts | `unrecognized_verdict_count` | <= 0 |

`recomputed_pass_count` is in `info["metrics"]` and `info["score"]` (with
the number of requirements recomputed as unknown) and is not a gate.
`scripts/run_ladder.py` prints its mean per baseline.

## What the evaluator computes

`src/aedl/evaluators/requirements_bundle.py`:

1. **Requirement set.** The eight machine-checkable requirements are read
   from the SysML model with `sysml2kit.interop.requirements.extract_requirements`
   (REQ-LINK-MARGIN, REQ-SLL, REQ-INDEP-LINK, REQ-CLEARSKY-AGREE,
   REQ-GAIN-XCHECK, REQ-POWER, REQ-COST, REQ-GRATING), with their operators
   and thresholds. t1-001's two requirements are added as ELEM-S11-IN-BAND
   and ELEM-FOOTPRINT, ten in all. Element limits come from t1-001's
   TaskSpec bounds.
2. **Recomputation.** The submitted architecture goes through the t3-001
   evaluator (`satcom_terminal`): phased-array-systems over t3-001's held-out
   envelope and failure seeds, the PAM full-pattern recompute, and the
   opensatcom link cross-check. Each SysML requirement is checked against the
   metric its `metricKey` names. The element spec goes through the t1-001
   evaluator at its analytic tier. The board is regenerated from the element
   spec with antenna-cad's KiCad emitter. Nothing the bundle claims enters
   this step.
3. **Scoring.**
   - `verdict_agreement`: requirements whose submitted status agrees with the
     recomputed one, over ten. A missing verdict disagrees. See the unknown
     rule below.
   - `actual_agreement`: requirements whose submitted `actual` is within
     tolerance of the recomputed value, over ten. A null actual agrees only
     on a requirement recomputed as unknown.
   - `provenance_completeness`: over the ten requirements, the fraction
     accounted for. An `unknown` verdict with a null
     actual is accounted for. Otherwise the actual must be a number and its
     `provenance` must have a SHA-256 `artifact_hash` (64 hex digits,
     `sha256:` prefix optional), a non-empty `capability`, an `origin` in
     {derived, vendor_claimed, imported, measured, assumed}, and a `fidelity`
     in {analytic, fullwave_open, fullwave_commercial, measured}. A missing
     verdict and a pass/fail verdict without a number are incomplete, so
     nulling numbers does not shrink the denominator. Verdicts for ids that
     are not task requirements are not in the denominator either (padding
     the bundle with fake `unknown` ids used to dilute it).
   - `unrecognized_verdict_count`: submitted verdict ids that are not one of
     the ten requirements, gated at 0. The ids are listed in
     `info["unrecognized_verdicts"]`.
   - `board_valid`: the board path stays inside the bundle and ends in
     `.kicad_pcb`. The file must be one balanced S-expression whose head is
     `kicad_pcb`, with a `(version <integer>)` child and a `(generator ...)`
     child. `board_provenance` must be a complete record whose hash equals the
     shipped file's SHA-256. The file must also be byte-identical to what
     `antenna_cad.backends.kicad.write_kicad_project` emits for the submitted
     element spec.

## Honest unknown

The recomputation marks a requirement `unknown` when its tier cannot
certify it. The element evaluator names those metrics in
`info["screening_metrics"]`. At t1-001's analytic tier that is the in-band
S11, so ELEM-S11-IN-BAND is recomputed as unknown, with the analytic
pass/fail kept as its screening status. Agreement on such a requirement:

- a submitted `unknown` agrees;
- a submitted `pass` or `fail` agrees only if it equals the screening status
  and its provenance says `fidelity: analytic`. The same verdict labelled
  `fullwave_open` disagrees, because it presents a screen as a certified
  result;
- a submitted `unknown` on a requirement the tier does certify disagrees.

## Tolerances for actual agreement

Set in `evaluator.params.actual_tolerance_by_suffix`, matched on the metric
name's suffix:

| suffix | metrics | tolerance |
|---|---|---|
| `_db` | margins, sidelobes, cross-check disagreements, S11 | 0.1 dB absolute |
| `_w` | prime power | 1 % |
| `_usd` | unit cost | 1 % |
| `_lambda` | grating margin | 0.005 wavelengths |
| `_mm` | footprint | 0.01 mm |

They allow rounding and assume the bundle's numbers come from the library
versions AEDL scores with. The EdgeArray hero bundle (below) was the first
tool-generated bundle, and it did not move them: its disagreements with the
recompute are 5 dB and 18 %, not tolerance-sized, and the library drift
measured beside it (next section) is a reason to pin versions, not to widen
a 0.1 dB tolerance to 2.7 dB.

## Thresholds for ten requirements

One wrong verdict or one number out of tolerance is tolerated (9/10 = 0.9),
two are not (0.8). For provenance, one unaccounted requirement out of ten
fails (0.9 < 0.95), so every number needs a complete record.

## Board regeneration

antenna-cad 0.2's emitter is deterministic: UUIDs are derived from the
design name, and the output depends only on the DesignSpec and the
antenna-cad version, which the file records as `generator_version`. So the
evaluator requires the shipped board to be exactly the regenerated one.
This ties the board to the element spec, at the cost of coupling to the
antenna-cad version. A bundle produced with a different antenna-cad
release fails `board_valid` even if its board is correct for that release.
`info["board"]` reports the shipped and expected hashes, so a version
mismatch is visible.

Two emissions are accepted. EdgeArray stores the synthesized design as an
IR file (polygons as WKT, rounded to six decimals) and emits the board from
that file, so its board differs from a direct emission in a few coordinates
by up to 1e-6 mm: `(at 4.801576 7.12609)` against `(at 4.801577 7.12609)`,
and four polygon vertices one unit in the sixth decimal apart. The design's
content hash is the same either way. The evaluator computes both, accepts a
shipped board equal to either, and reports `regeneration: "ok (emitted from
the stored IR)"` for the second. This was the one recalibration the hero
bundle needed. An edited board with an honest hash still fails.

The dual acceptance is a workaround, kept deliberately. The cause is in
antenna-cad: its IR rounds coordinates to six decimals on `to_dict`, but
`to_design` and the emitter do not round the same way, so the direct and
stored-IR emissions disagree in the last digit. The fix belongs upstream
(AEDL CLAUDE.md: fix library bugs upstream rather than working around them),
and antenna-cad is a separate published repository outside this change set.
It is tracked in `docs/roadmap.md` under "Upstream fixes needed": round IR
coordinates consistently in `to_design` and the emitter so the two emissions
are byte-identical, after which the second accepted hash is removed. Accepting
both does not loosen the check: each is a board antenna-cad emits for the
submitted element spec.

## Deviation from the task brief: the architecture section

The brief lists the array config as nx, ny, spacing and taper. Seven of the
eight system requirements depend on more than that: link margin and prime
power on per-element power and PA class, cost on the phase-shifter bits and
digitization, sidelobes on quantization. So the bundle's `architecture` is
t3-001's full architecture (array, rf, digital), with t3-001's validation
rules. The task context carries t3-001's parts table and envelope bounds and
t1-001's laminate data, and `tests/test_t4_001.py` fails if either copy drifts
from its source task.

## Reference and baseline bundles

`reference/submission/` is synthetic (see `reference/README.md`). Its
architecture is the t3-001 reference design, its element spec is the t1-001
reference, its board comes from antenna-cad's KiCad emitter, and its verdicts
are the evaluator's own recomputation, with ELEM-S11-IN-BAND reported as
unknown. It recomputes to 9 passes and 1 unknown and scores 1.0 on all four
gated metrics. That shows the evaluator accepts a correct bundle and that
every certifiable requirement can be closed at once. It says nothing about
whether a tool can produce such a bundle, and the tests use it as the
known-good input.

`reference/edgearray_hero/submission/` is the B0 baseline data point on
t4-001 (EdgeArray's hero workflow, rules only, no LLM) and is not a
reference. It was generated by `edgearray workflow hero` (deterministic,
analytic EM solver) and
converted by `scripts/bundle_from_edgearray.py`, which reads the workflow's
on-disk outputs and imports nothing from EdgeArray. The field mappings are
at the top of the script; commands and versions are in `reference/README.md`.
**It does not pass**: verdict_agreement 0.5 (gate 0.9), actual_agreement 0.3
(gate 0.9), provenance_completeness 1.0, board_valid 1.0. t4-001 therefore
has no tool-generated reference that clears its own gates.
`tests/test_t4_001.py` pins the scores and the causes below.

### Why the hero bundle fails

The hero's SatcomTerminal28GHz run reports 4 pass and 4 unverified; its
model has no element requirements. Per requirement (AEDL numbers from
AEDL's environment; the last column reruns the same AEDL evaluator in
EdgeArray's environment to isolate library drift):

| id | hero | AEDL recompute | AEDL, EdgeArray libs | result |
|---|---|---|---|---|
| REQ-GAIN-XCHECK | pass, 0.0251 dB | pass, 0.0720 dB | 0.0196 dB | agrees (0.047 dB apart, tolerance 0.1) |
| REQ-GRATING | pass, 0.035898 | pass, 0.035898 | 0.035898 | agrees |
| REQ-SLL | pass, -22.32 dB | pass, -17.31 dB | -19.79 dB | status agrees, number 5.0 dB off |
| REQ-POWER | pass, 368.64 W | pass, 436.59 W | 436.59 W | status agrees, number 18 % off |
| REQ-CLEARSKY-AGREE | unverified | pass, 0.302 dB | 0.249 dB | hero abstains |
| REQ-COST | unverified | fail, 48640 USD | 48640 USD | hero abstains |
| REQ-INDEP-LINK | unverified | pass, 14.878 dB | 14.521 dB | hero abstains |
| REQ-LINK-MARGIN | unverified | pass, 3.308 dB | 3.308 dB | hero abstains |
| ELEM-FOOTPRINT | not in model | pass, 5.607 mm | | hero abstains |
| ELEM-S11-IN-BAND | not in model | unknown (screen: fail, -4.61 dB) | | agrees (both unknown) |

Verdict agreement is 5 of 10: the four unverified requirements and the
element footprint. The evaluator counts an `unknown` on a requirement it can
certify as a disagreement, by design (see Honest unknown), so a workflow that
declines half the requirements cannot clear a 0.9 gate. Actual agreement is
3 of 10: GAIN-XCHECK, GRATING, and ELEM-S11-IN-BAND (null on an unknown).
The causes of the two number disagreements:

- **REQ-POWER.** The hero's 368.64 W is 307.2 W of PA DC power times PAS's
  1.2 overhead factor. The task's parts table adds the receive chain
  (0.15 W per element, 38.4 W) and, at element digitization, ADC (13.1 W) and
  DSP (5.1 W) power: (307.2 + 38.4 + 13.1 + 5.1) x 1.2 = 436.59 W. The hero's
  study has no receive or digital section, so it could not include them.
- **REQ-SLL.** The hero takes the worst sidelobe over scan angles 0 to 60
  degrees in the phi = 0 and phi = 90 planes, with ideal phase shifters, no
  element failures and a cos^1.5 element. AEDL integrates the full sphere
  at the binding scan, with 6-bit phases, 2 % seeded failures and cos^1.3.
  In AEDL's environment the same weights give -20.0 dB with ideal phases
  and no failures at 60 degrees, -19.4 dB with 6-bit phases, and -17.3 to
  -19.0 dB across the five failure seeds. In EdgeArray's environment the
  same AEDL code gives -22.7, -22.3 and -19.8 to -21.9 dB. So about 2.7 dB of
  the 5.0 dB is the phased-array-modeling version (1.4.0 against 1.5.0), and
  the rest is the failures, quantization and element exponent the hero's
  number leaves out.
- **REQ-COST.** The hero does not compute a unit cost. AEDL prices the
  architecture at 150 USD per element (55 + 45 + 50 for the PA class B and
  6-bit shifter) plus 40 USD per digital channel. The converter had to fill
  in the digital section (below); at element digitization 256 channels cost
  10240 USD and the total, 48640 USD, exceeds 45000. With sub-array
  digitization (4 channels) the total would be 38560 USD and the requirement
  would pass. The hero gives no basis for either choice.

### What the converter filled in

The hero does not choose the phase-shifter resolution or the digitization
that t3-001's architecture requires. The converter sets `phase_bits` to 6
(the hero's patterns assume no quantization), `digitization_level` to
`element` and `adc_enob` to 12.0 (PAS's `DigitalConfig` defaults, which the
hero's study ran with), and takes the sub-array size from the hero's tiling
rule. `rf.pa_class` is the parts-table class whose efficiency equals the
hero's assumed 0.25 (class B). These values are listed in `conversion.json`
and printed on stderr. They affect the recompute (COST above), so the
failure is partly about the bundle format needing more than the hero decides.

The converter labels a verdict's origin `assumed` when the hero's report
warns that it was "checked on assumed inputs", and `derived` otherwise. For
this run all four verified verdicts are `assumed`: the three array verdicts
rest on an assumed element pattern exponent, and REQ-POWER on assumed
transmit power, PA efficiency, noise figure and others. Origin does not enter
any gate, so the scores are unchanged (0.5, 0.3, 1.0, 1.0).

### Library drift

The same architecture scored in AEDL's environment (phased-array-systems
0.10.1, phased-array-modeling 1.4.0, opensatcom 0.6.0) and in EdgeArray's
(0.14.1, 1.5.0, 0.7.0) differs by: GAIN-XCHECK 0.052 dB, CLEARSKY 0.052 dB,
INDEP-LINK 0.357 dB, SLL 2.48 dB; LINK-MARGIN, POWER, COST and GRATING are
identical. Two of those exceed the 0.1 dB tolerance. The pyproject ranges
(`phased-array-modeling>=1.4,<2.0`) allow either environment, so t3-001 and
t4-001 scores depend on which one is installed. The tolerances stay as they
are, because widening `_db` to cover the 2.5 dB would also accept a claim that
is 2.5 dB wrong; the fix is to score in one pinned environment. The scanned
sidelobe change between phased-array-modeling 1.4.0 and 1.5.0 is the larger
risk to t3-001's calibration and has not been investigated here.

### Element finding

The hero designs its patch at 28.0 GHz center, 50 ohm, on 0.508 mm RO4350B.
t1-001's cavity model puts the worst in-band |S11| at -4.6 dB (screen: fail),
so the element would not meet -10 dB over 27.5 to 28.5 GHz even if the tier
could certify it. The hero's own analytic estimate puts the resonance at
27.32 GHz, 2.4 % below its design frequency.

## Calibration: each requirement catches a specific defect

Pinned in `tests/test_t4_001.py`:

| defect | caught by |
|---|---|
| two statuses flipped, or two verdicts missing | verdict-agreement (8/10) |
| a full-wave label on the analytic S11 screen, or a verdict contradicting it | verdict-agreement |
| architecture changed (0.5 W per element, uniform taper) with the old verdicts kept | verdict-agreement and actual-agreement |
| two numbers out of tolerance (1 dB on a margin, 5 % on power) | actual-agreement (8/10) |
| one provenance record removed, a pass verdict with its number nulled, or a missing verdict | provenance (9/10) |
| origin `guessed`, fidelity `full_wave`, a malformed or newline-padded hash, or an empty capability | provenance |
| truncated board, a schematic instead of a PCB, missing version or generator, trailing content, unterminated string | board |
| board path outside the bundle, missing, or not `.kicad_pcb` | board |
| board_provenance missing or naming a different hash | board |
| a well-formed board edited by one token, with an honest hash | board (regeneration) |
| the review's degenerate bundle: one-line board, one fabricated provenance record, statuses copied with every number nulled | actual-agreement, provenance, board |
| the EdgeArray hero bundle: half the requirements left unverified, SLL and power computed without the task's failures, quantization and parts table | verdict-agreement (0.5) and actual-agreement (0.3) |
| a board emitted from the stored IR (six-decimal polygons) | accepted; an edited one still fails board |
| element spec path outside the bundle, unknown bundle keys, a status other than pass/fail/unknown | rejected as malformed |

## Testing

The t4 tests need the `systems`, `element` and `sysml` extras and run the
t3-001 evaluator several times, about 70 s in all. CI installs
`.[dev,element]`, so the t1 tests run there and the t4 tests, like the t3
tests, skip. They are meant for a nightly or local run with all extras.

## Known limits

- Verdict hashes are checked for form only. A bundle can cite the hash of
  an artifact it does not ship. The board hash is the one that gets resolved.
- The element and the array are scored independently. The t3-001 system
  model uses a cos^q element pattern from its own context, not the submitted
  patch.
- Evaluation takes about 20 s (one t3-001 evaluation, one t1-001 evaluation,
  two board emissions, direct and via the stored IR).
- The agent faces t3-001's held-out envelope, so results on t3-001 and
  t4-001 are not independent measurements of system design skill.
