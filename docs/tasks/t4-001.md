# t4-001: requirements to board

Tier 4 (cross-layer). The agent starts from the SysML v2 model
`SatcomTerminal28GHz` (sysml2kit-rf-library, model name
`satcom-terminal-t3001`) and submits a design bundle: a terminal
architecture, a patch element DesignSpec, a KiCad board for the element, and
a verdict for every requirement, each reported number carrying a provenance
record. The task scores the bundle's honesty and completeness; how many
requirements the design closes is reported beside the verdict as a score.

Requirements (`tasks/t4-001-requirements-to-board/task.yaml`):

| id | metric | limit |
|---|---|---|
| verdict-agreement | `verdict_agreement` | >= 0.9 |
| provenance | `provenance_completeness` | >= 0.95 |
| board | `board_valid` | >= 1 |

`recomputed_pass_count` is in `info["metrics"]` and `info["score"]` and is
not a gate.

## What the evaluator computes

`src/aedl/evaluators/requirements_bundle.py`:

1. **Requirement set.** The eight machine-checkable requirements are read
   from the SysML model with `sysml2kit.interop.requirements.extract_requirements`
   (REQ-LINK-MARGIN, REQ-SLL, REQ-INDEP-LINK, REQ-CLEARSKY-AGREE,
   REQ-GAIN-XCHECK, REQ-POWER, REQ-COST, REQ-GRATING), with their operators
   and thresholds. The four t1-001 element requirements are added as
   ELEM-S11-IN-BAND, ELEM-FOOTPRINT, ELEM-F-RES-LO and ELEM-F-RES-HI, twelve in all.
2. **Recomputation.** The submitted architecture goes through the t3-001
   evaluator (`satcom_terminal`): phased-array-systems over t3-001's held-out
   envelope and failure seeds, the PAM full-pattern recompute, and the
   opensatcom link cross-check. Each SysML requirement is checked against the
   metric its `metricKey` names. The element spec goes through the t1-001
   evaluator at its analytic tier. Nothing from the bundle's verdicts enters
   this step.
3. **Scoring.**
   - `verdict_agreement`: requirements whose submitted status equals the
     recomputed status, over twelve. A missing verdict disagrees. Verdict ids
     the evaluator does not recognize are listed in
     `info["unrecognized_verdicts"]` and do not count.
   - `provenance_completeness`: over every verdict with a numeric `actual`,
     the fraction whose `provenance` has a SHA-256 `artifact_hash` (64 hex
     digits, `sha256:` prefix optional), a non-empty `capability`, an `origin`
     in {derived, vendor_claimed, imported, measured, assumed}, and a
     `fidelity` in {analytic, fullwave_open, fullwave_commercial, measured}.
   - `board_valid`: the board path stays inside the bundle, ends in
     `.kicad_pcb`, and the file is one balanced S-expression whose head is
     `kicad_pcb` with a `(version <integer>)` child and a `(generator ...)`
     child.

The thresholds work out as follows for twelve requirements: one wrong or
missing verdict is tolerated (11/12 = 0.917), two are not (0.833). For
provenance, one incomplete record out of twelve numbers fails (0.917 < 0.95),
so in practice every reported number needs a complete record.

## Deviation from the task brief: the architecture section

The brief lists the array config as nx, ny, spacing and taper. Seven of the
eight system requirements depend on more than that: link margin and prime
power on per-element power and PA class, cost on the phase-shifter bits and
digitization, sidelobes on quantization. So the bundle's `architecture` is
t3-001's full architecture (array, rf, digital), with t3-001's validation
rules. The task context carries t3-001's parts table and envelope bounds and
t1-001's laminate data, and `tests/test_t4_001.py` fails if either copy drifts
from its source task.

## Reference bundle: synthetic, for now

`reference/submission/` is synthetic (see `reference/README.md`). Its
architecture is the t3-001 reference design, its element spec is the t1-001
reference, its board comes from antenna-cad's KiCad emitter, and its verdicts
are the evaluator's own recomputation. It recomputes to 12/12 passes and
scores 1.0 on all three metrics. That establishes that the evaluator accepts
a correct bundle and that every requirement is closable together. It says
nothing about whether a tool can produce one. A follow-up replaces it with a
bundle converted from EdgeArray's hero workflow (`edgearray workflow hero`,
which does not exist yet); the conversion command will be recorded here.

## Calibration: each requirement catches a specific defect

Pinned in `tests/test_t4_001.py`:

| defect | caught by |
|---|---|
| two statuses flipped | verdict-agreement (10/12) |
| two verdicts missing | verdict-agreement (10/12) |
| architecture changed (0.5 W per element, uniform taper) with the old verdicts kept | verdict-agreement: REQ-POWER and REQ-SLL recompute to fail |
| one provenance record removed | provenance (11/12) |
| origin `guessed`, fidelity `full_wave`, hash `abc123`, or empty capability | provenance |
| truncated board, a schematic instead of a PCB, missing version or generator, trailing content, unterminated string | board |
| board path outside the bundle, missing, or not `.kicad_pcb` | board |
| element spec path outside the bundle, unknown bundle keys, a status other than pass/fail/unknown | rejected as malformed |

One flipped verdict passes, by design of the 0.9 threshold.

## Known limits

- Hashes are checked for form only. A bundle can cite the hash of an
  artifact it does not ship, and the evaluator does not check that the hash
  matches the file the number came from.
- The board is checked for structure, not content. Nothing confirms that it
  realizes the submitted element spec or the array.
- The element and the array are scored independently. The t3-001 system
  model uses a cos^q element pattern from its own context, not the submitted
  patch.
- Evaluation takes about 20 s (one t3-001 evaluation plus one t1-001
  evaluation).
- The agent faces t3-001's held-out envelope, so results on t3-001 and
  t4-001 are not independent measurements of system design skill.
